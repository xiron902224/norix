# Compose stacks

A **compose stack** is a `docker-compose.yml` from Git that Norix runs as one unit. The agent clones the repository and runs `docker compose up` with the file as written. Volumes, `command`, `entrypoint`, healthchecks, `depends_on` conditions, `restart: "no"` jobs and relative bind mounts behave as they do on your laptop.

## Deploy a stack

1. Open a project → **Compose stack**.
2. Fill **Stack name**, **Git URL**, **Ref** and **Compose file** (path inside the repo, for example `deploy/docker-compose.yml`).
3. Optional, in the same form:
   - **Public services**: comma-separated service names that keep their host ports. All other services are internal.
   - **Domains**: one `service=hostname` per line. Norix routes the hostname to that service over HTTPS/WSS (see [Domains](#domains)).
   - **Variables**: one `NAME=value` per line for `${NAME}` interpolation (see [Variables](#variables)).
4. Choose:
   - **Deploy stack**: queue it now. Use this for private repositories that only the agent can clone (SSH key on the node).
   - **Analyze compose**: the control plane clones the repo and lists the services first. This needs a repository the control plane can reach.
5. The stack card shows the status and every service. A node with Docker claims the stack on its next heartbeat.

What the agent runs, in `<agent workdir>/stacks/<stack id>/`:

```bash
git clone --depth 1 --branch <ref> <url> src     # later deploys: fetch + reset --hard
docker compose -p norix-<stack id prefix> --env-file stack.env \
  -f src/<compose file> -f norix.override.yml \
  up -d --build --remove-orphans
```

`norix.override.yml` is generated by Norix. It labels every service, joins the project network, sets the service aliases, and removes host ports from internal services. `stack.env` holds the variables for interpolation. It is written with mode `0600` and removed after each apply. The checkout is kept between deploys so relative bind mounts keep their data.

## Status

| Stack status | Meaning |
|---|---|
| `pending` | Waiting for a node, or for the next heartbeat after an action. |
| `deploying` | `docker compose up` is running, or a service is still `created` / health `starting`. |
| `running` | Every service is running and not unhealthy. A one-shot job that exited with code 0 counts as **Completed**. |
| `degraded` | A service is restarting, unhealthy, or exited with a non-zero code. |
| `stopped` | The stack was stopped, or no container exists. |
| `failed` | The last apply failed (clone, `compose config`, missing variable, bind outside the allowlist, build or `up`). The card shows the error. Fix it and click **Redeploy**. |
| `removing` | `docker compose down` is running. |

The build and `up` run in the background, so the agent keeps sending heartbeats during long builds. The default timeout is one hour. Change it with `NORIX_COMPOSE_UP_TIMEOUT_SECS` on the agent (60–21600).

## Networking

All stacks of a project share one Docker network, `norix-p-<project id hex>`, on the same node. Each service is reachable from other stacks of the project by two names:

- `<service>`: the name in the compose file, for example `db`.
- `<compose project>-<service>`, for example `norix-3f2504e0-db`. Use this one when you want a name that cannot collide.

A stack can also join a network that already exists on the node. Declare it in the compose file as `external: true`. Norix keeps the aliases you set on that network. This lets a stack reach a shared database without publishing a port.

## Public and internal services

Services are **internal by default**: Norix removes their host ports (`ports: !reset []`), so they are reachable only on the project network. Put a service in **Public services** to keep its published ports as written in the compose file.

## Domains

A domain sends HTTPS (and WebSocket `wss://`) traffic for a hostname to one service:

```text
web=app.example.com
api=api.example.com
```

Requirements:

- The service must declare a container port in the compose file (`ports` or `expose`). Without a port, Norix skips the domain.
- The node that runs the stack must also run the local Caddy edge (the container labeled `caddy`). Norix joins Caddy to the project network and routes to `http://norix-<id>-<service>:<port>`.
- The DNS record for the hostname must point at the node's edge. Caddy manages the TLS certificate.

Routes are replaced as a whole on each edge plan, so a stopped or removed stack drops out of Caddy on the next plan.

## Variables

Set variables in the form or in **Settings** on the card. Values are write-only:

- Values are sent once and stored encrypted (AES-GCM). The API returns names only, and the card lists them without values.
- To change a value, set it again. To remove a variable, send `NAME=` (empty value).
- Interpolation works as usual: `${DB_PASSWORD}`, `${DB_PASSWORD:-default}`. A missing required variable (`${DB_PASSWORD:?required}`) fails the apply and names the variable.
- `SERVICE_PASSWORD_<NAME>` (32 alphanumeric characters) and `SERVICE_BASE64_<NAME>` (32 random bytes, base64) are **generated once** when the file references them and reused on every later deploy. The values are not shown in the UI. They are kept encrypted in the control plane and in `generated.json` (mode `0600`) on the node.

Norix passes its variables with `--env-file`, so a `.env` committed in the repo is **not** read. Put non-secret defaults in the compose file (`${VAR:-default}`).

## Volumes and delete

The card lists each volume the stack uses as `named` or `bind`.

| Button | Agent runs |
|---|---|
| **Start** / **Redeploy** | `git fetch` + `docker compose up -d --build --remove-orphans` |
| **Stop** | `docker compose stop` |
| **Delete** | `docker compose down --remove-orphans`. **Named volumes and the checkout are kept.** |
| **Delete** with **Purge volumes on delete** checked | `docker compose down --remove-orphans --volumes`, then removes the checkout. **This cannot be undone.** |

Other rules:

- A bind mount must stay inside the checkout, or inside a path listed in the agent's `NORIX_COMPOSE_BIND_ALLOWLIST` (comma-separated absolute paths). Otherwise the apply fails before `up`.
- If `git fetch` fails, the agent keeps the checkout and reports the error. It never deletes bind data to recover.

Each action bumps the stack generation (`gen observed/desired` on the card).

## Logs

**Logs** on the card shows the last lines per service, plus `deploy output` (clone, build and `up`). Lines follow the [log retention](./ops.md#log-retention) policy: each service counts like one workload. Secret values are redacted from output.

## Placement

All stacks of a project run on the **same node**, so they can share the project network. A stack stays on its node. Norix does not move it, because its volumes live there.

## Private repositories

The agent clones as the user that runs `norix-agent`, with `GIT_TERMINAL_PROMPT=0`. For private GitHub/GitLab repos, add a read-only deploy key to that user's `~/.ssh` and use an SSH URL (`git@github.com:org/repo.git`). Do not put tokens in the URL. They end up in `.git/config` on the node. Norix redacts `user:token@` from logged git output.

## Legacy: split into workloads

After **Analyze compose**, **Split into workloads (legacy)** still turns each service into a separate Norix workload (old behavior). That mode ignores volumes, commands, healthchecks, `restart`, and the networking and variable features above. Use it only for simple image-only stacks that need per-service scaling or rolling updates.
